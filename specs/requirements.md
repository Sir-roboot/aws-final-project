# Requirements Document

## Introduction

This document defines the requirements for a secure, scalable, and highly available PHP web application infrastructure on AWS. The project addresses the needs of a non-profit organization (Example Social Research Organization) that provides a website with global development data. Due to growing popularity, the current hosting has become slow and vulnerable to attacks. The solution must guarantee security, scalability, and availability using AWS services, deployed entirely via Terraform as Infrastructure as Code.

The project is developed within the AWS Academy Learner Lab environment with specific budget, service, and configuration constraints.

## Glossary

- **ALB**: Application Load Balancer — an AWS Elastic Load Balancing service that distributes incoming HTTP traffic across multiple targets in multiple Availability Zones.
- **ASG**: Auto Scaling Group — an AWS service that automatically adjusts the number of EC2 instances based on demand or health checks.
- **RDS**: Amazon Relational Database Service — a managed database service for MySQL.
- **VPC**: Virtual Private Cloud — an isolated virtual network within AWS.
- **EC2**: Elastic Compute Cloud — virtual server instances running the PHP application.
- **NAT_Gateway**: Network Address Translation Gateway — enables instances in private subnets to access the internet for outbound traffic.
- **IGW**: Internet Gateway — enables communication between the VPC and the internet.
- **SSM**: AWS Systems Manager — provides Session Manager for secure shell access without SSH ports.
- **Secrets_Manager**: AWS Secrets Manager — stores and retrieves database credentials securely.
- **Launch_Template**: An EC2 configuration template specifying AMI, instance type, security groups, IAM role, and user data for ASG instances.
- **User_Data**: A bootstrap script executed when an EC2 instance launches, used to install software and configure the application.
- **Terraform**: An Infrastructure as Code tool used to provision and manage all AWS resources declaratively.
- **Security_Group**: A virtual firewall controlling inbound and outbound traffic for AWS resources.
- **Public_Subnet**: A subnet with a route to the Internet Gateway, hosting the ALB and NAT Gateway.
- **Private_Subnet**: A subnet without direct internet access, hosting EC2 application instances.
- **DB_Subnet**: A subnet dedicated to hosting the RDS database instance.
- **Availability_Zone**: An isolated location within an AWS region providing redundancy.
- **Target_Tracking_Policy**: An Auto Scaling policy that adjusts capacity to maintain a specified metric target.
- **Countries_Database**: The MySQL database named "countries" containing the countrydata_final table.
- **Countrydata_Final_Table**: The database table containing development statistics for 214 countries.
- **Example_Zip**: The provided PHP application archive downloaded during instance bootstrap.
- **Countrydatadump_SQL**: The SQL dump file containing 214 country records to be imported into the countries database.

## Requirements

### Requirement 1: MySQL Database Provisioning on Amazon RDS

**User Story:** As a cloud architect, I want to create a managed MySQL database on Amazon RDS, so that the PHP application has a reliable and secure data store for global development statistics.

#### Acceptance Criteria

1. THE Terraform SHALL provision exactly one Amazon RDS MySQL instance in the AWS account.
2. THE Terraform SHALL configure the RDS instance with the database name "countries".
3. THE Terraform SHALL enable "Manage master credentials in AWS Secrets Manager" so that the generated secret has the prefix "rds!db-".
4. THE Terraform SHALL place the RDS instance in DB_Subnet groups spanning at least 2 Availability Zones.
5. THE Terraform SHALL set the RDS instance to NOT be publicly accessible.
6. THE Terraform SHALL configure the RDS Security_Group to allow inbound traffic on port 3306 only from the EC2 application Security_Group.
7. IF the RDS instance fails a health check, THEN THE RDS SHALL remain accessible through the configured subnet group without manual intervention.

### Requirement 2: Credential Management via AWS Secrets Manager

**User Story:** As a security engineer, I want database credentials stored in AWS Secrets Manager with RDS-managed rotation, so that no credentials are hardcoded in application code or infrastructure configuration.

#### Acceptance Criteria

1. THE Terraform SHALL configure RDS to manage master credentials in Secrets_Manager automatically.
2. THE Secrets_Manager secret SHALL have a name with the prefix "rds!db-" as generated by the RDS managed credentials feature.
3. THE Terraform SHALL NOT include any hardcoded database passwords in source files, variables, or outputs.
4. WHEN the PHP application requests credentials, THE Secrets_Manager SHALL return the current username and password for the countries database.
5. THE EC2 instances SHALL have IAM permissions to read secrets from Secrets_Manager via their instance profile.

### Requirement 3: Network Architecture with VPC and Subnets

**User Story:** As a network architect, I want a properly segmented VPC with public, private, and database subnets across multiple Availability Zones, so that the infrastructure follows defense-in-depth principles.

#### Acceptance Criteria

1. THE Terraform SHALL create a VPC in the us-east-1 region.
2. THE Terraform SHALL create Public_Subnets in at least 2 Availability Zones for the ALB and NAT_Gateway.
3. THE Terraform SHALL create Private_Subnets in at least 2 Availability Zones for EC2 application instances.
4. THE Terraform SHALL create DB_Subnets in at least 2 Availability Zones for the RDS instance.
5. THE Terraform SHALL create an Internet Gateway attached to the VPC.
6. THE Terraform SHALL create at least one NAT_Gateway in a Public_Subnet to provide outbound internet access for Private_Subnet instances.
7. THE Terraform SHALL configure route tables so that Public_Subnets route internet traffic through the IGW.
8. THE Terraform SHALL configure route tables so that Private_Subnets route internet traffic through the NAT_Gateway.
9. THE Terraform SHALL configure route tables so that DB_Subnets have no route to the internet.

### Requirement 4: Application Load Balancer Deployment

**User Story:** As a site reliability engineer, I want an Application Load Balancer distributing traffic across multiple web servers, so that the application is highly available and can handle increased traffic.

#### Acceptance Criteria

1. THE Terraform SHALL deploy an ALB in Public_Subnets across at least 2 Availability Zones.
2. THE ALB SHALL listen on port 80 for HTTP traffic from the internet.
3. THE ALB SHALL forward traffic to a target group containing EC2 instances from the ASG.
4. THE ALB Security_Group SHALL allow inbound traffic on port 80 from 0.0.0.0/0.
5. WHEN a request is received, THE ALB SHALL distribute it to a healthy EC2 instance and return an HTTP 200 response with the PHP application content.
6. THE ALB SHALL perform health checks against the EC2 target instances to route traffic only to healthy targets.

### Requirement 5: Auto Scaling Group with Launch Template

**User Story:** As a cloud architect, I want an Auto Scaling Group with a Launch Template that automatically provisions and scales web servers, so that the application maintains availability under varying load.

#### Acceptance Criteria

1. THE Terraform SHALL create a Launch_Template specifying Amazon Linux 2023 AMI and t2.micro instance type.
2. THE Terraform SHALL configure the Launch_Template to NOT assign public IP addresses to instances.
3. THE Terraform SHALL configure the Launch_Template with an IAM instance profile granting SSM and Secrets_Manager read permissions.
4. THE Terraform SHALL configure the Launch_Template with a User_Data script that bootstraps the PHP application.
5. THE Terraform SHALL create an ASG that launches instances in Private_Subnets across at least 2 Availability Zones.
6. THE Terraform SHALL configure the ASG with a target tracking scaling policy.
7. THE ASG SHALL register launched instances with the ALB target group automatically.
8. WHEN an instance becomes unhealthy, THE ASG SHALL terminate it and launch a replacement instance.

### Requirement 6: EC2 Instance Bootstrap via User Data

**User Story:** As a DevOps engineer, I want EC2 instances to automatically install and configure the PHP application on launch, so that new instances are immediately ready to serve traffic without manual intervention.

#### Acceptance Criteria

1. WHEN an EC2 instance launches, THE User_Data script SHALL install Apache HTTP Server (httpd).
2. WHEN an EC2 instance launches, THE User_Data script SHALL install PHP and required PHP modules.
3. WHEN an EC2 instance launches, THE User_Data script SHALL install the MariaDB client (mariadb105).
4. WHEN an EC2 instance launches, THE User_Data script SHALL download and extract Example_Zip to /var/www/html.
5. WHEN an EC2 instance launches, THE User_Data script SHALL apply the lifeexpectancy.php bug fix using sed to replace $_SESSION variables with direct variables ($ep, $un, $pw, $db) on line 6.
6. WHEN an EC2 instance launches, THE User_Data script SHALL start and enable the Apache HTTP Server.
7. WHEN an EC2 instance launches, THE User_Data script SHALL configure the application to retrieve database credentials from Secrets_Manager.

### Requirement 7: Security Group Configuration

**User Story:** As a security engineer, I want properly configured security groups enforcing least-privilege network access, so that each tier only communicates with its authorized adjacent tier.

#### Acceptance Criteria

1. THE Terraform SHALL create an ALB Security_Group allowing inbound HTTP (port 80) from 0.0.0.0/0.
2. THE Terraform SHALL create an EC2 Security_Group allowing inbound HTTP (port 80) only from the ALB Security_Group.
3. THE Terraform SHALL create an RDS Security_Group allowing inbound MySQL (port 3306) only from the EC2 Security_Group.
4. THE EC2 Security_Group SHALL NOT allow inbound traffic on port 22 (SSH).
5. THE Terraform SHALL NOT open any ports beyond those explicitly required for application functionality.
6. THE Security_Groups SHALL allow outbound traffic as needed for application operation (internet access via NAT for updates, Secrets Manager API calls, and database connectivity).

### Requirement 8: IAM Role and Instance Profile

**User Story:** As a security engineer, I want EC2 instances to have an IAM role with minimum required permissions, so that the application can access AWS services without storing credentials on the instance.

#### Acceptance Criteria

1. THE Terraform SHALL create an IAM role for EC2 instances with the AmazonSSMManagedInstanceCore managed policy.
2. THE Terraform SHALL attach permissions to the IAM role allowing read access to Secrets_Manager secrets.
3. THE Terraform SHALL attach permissions to the IAM role allowing read access to RDS instance metadata (describe-db-instances).
4. THE Terraform SHALL create an instance profile associating the IAM role with EC2 instances in the Launch_Template.
5. THE IAM role SHALL NOT grant permissions beyond SSM, Secrets_Manager read, and RDS describe operations.

### Requirement 9: SQL Data Import Process

**User Story:** As a database administrator, I want to import the country development data into the RDS database, so that the PHP application can serve queries about 214 countries.

#### Acceptance Criteria

1. WHEN the infrastructure is deployed, THE administrator SHALL connect to an EC2 instance via SSM Session Manager to perform the data import.
2. THE import process SHALL download Countrydatadump_SQL from the provided S3 URL (https://aws-tc-largeobjects.s3.us-west-2.amazonaws.com/CUR-TF-200-ACACAD-3-113230/22-lab-Capstone-project/s3/Countrydatadump.sql).
3. THE import process SHALL retrieve database credentials from Secrets_Manager using the AWS CLI.
4. THE import process SHALL obtain the RDS endpoint using the AWS CLI (describe-db-instances).
5. WHEN the import completes, THE Countries_Database SHALL contain the Countrydata_Final_Table with exactly 214 rows.
6. THE Terraform outputs SHALL include instructions or a script for performing the SQL import via SSM.

### Requirement 10: PHP Application Functionality

**User Story:** As an end user, I want to access the web application through the ALB and run queries about global development data, so that I can research country statistics.

#### Acceptance Criteria

1. WHEN a user accesses the ALB DNS name via HTTP, THE application SHALL display the PHP web interface.
2. THE application SHALL provide Query 1 (Mobile Phones) returning valid data from the Countrydata_Final_Table.
3. THE application SHALL provide Query 2 (Population) returning valid data from the Countrydata_Final_Table.
4. THE application SHALL provide Query 3 (Life Expectancy) returning valid data from the Countrydata_Final_Table after the bug fix is applied.
5. THE application SHALL provide Query 4 (GDP) returning valid data from the Countrydata_Final_Table.
6. THE application SHALL provide Query 5 (Childhood Mortality) returning valid data from the Countrydata_Final_Table.
7. IF the database connection fails, THEN THE application SHALL display a connection error message rather than exposing internal details.

### Requirement 11: Infrastructure as Code Organization

**User Story:** As a DevOps engineer, I want the Terraform code organized into logical, well-named files, so that the infrastructure is maintainable and reviewable.

#### Acceptance Criteria

1. THE Terraform project SHALL include a providers.tf file defining the AWS provider for us-east-1.
2. THE Terraform project SHALL include a variables.tf file defining all configurable parameters with descriptions and defaults.
3. THE Terraform project SHALL include a network.tf file containing VPC, subnets, route tables, IGW, and NAT Gateway resources.
4. THE Terraform project SHALL include a security_groups.tf file containing all Security_Group definitions.
5. THE Terraform project SHALL include an iam.tf file containing IAM roles, policies, and instance profiles.
6. THE Terraform project SHALL include an rds.tf file containing the RDS instance and subnet group.
7. THE Terraform project SHALL include an alb.tf file containing the ALB, target group, and listener.
8. THE Terraform project SHALL include an autoscaling.tf file containing the Launch Template, ASG, and scaling policy.
9. THE Terraform project SHALL include a userdata.sh.tpl file as a template for the EC2 bootstrap script.
10. THE Terraform project SHALL include an outputs.tf file exposing the ALB DNS name and other relevant endpoints.
11. THE Terraform project SHALL use a consistent naming convention with a project prefix for all resources.

### Requirement 12: Administrative Access via SSM

**User Story:** As a system administrator, I want to access EC2 instances through AWS Systems Manager Session Manager, so that I can perform maintenance tasks without opening SSH ports.

#### Acceptance Criteria

1. THE EC2 instances SHALL be accessible via SSM Session Manager without requiring port 22 to be open.
2. THE IAM instance profile SHALL include the AmazonSSMManagedInstanceCore policy to enable SSM connectivity.
3. THE Private_Subnet instances SHALL reach the SSM service endpoints through the NAT_Gateway.
4. WHEN an administrator connects via Session Manager, THE administrator SHALL be able to execute commands on the EC2 instance for database import and troubleshooting.

### Requirement 13: High Availability and Scalability

**User Story:** As a site reliability engineer, I want the application to maintain availability during instance failures and scale under load, so that users experience consistent performance.

#### Acceptance Criteria

1. THE ASG SHALL maintain a minimum number of instances across at least 2 Availability Zones.
2. WHEN an instance fails health checks, THE ASG SHALL launch a replacement in a healthy Availability Zone.
3. THE target tracking scaling policy SHALL adjust the number of instances based on a defined metric (such as average CPU utilization).
4. THE ALB SHALL distribute traffic only to healthy instances as determined by health check responses.
5. WHILE the ASG scales out, THE new instances SHALL automatically register with the ALB target group and begin serving traffic after passing health checks.

### Requirement 14: Lifeexpectancy.php Bug Fix

**User Story:** As a developer, I want the known bug in lifeexpectancy.php to be automatically fixed during instance bootstrap, so that Query 3 (Life Expectancy) works correctly on all instances including those created by Auto Scaling.

#### Acceptance Criteria

1. THE User_Data script SHALL replace the line `$conn = new mysqli($_SESSION["ep"], $_SESSION["un"], $_SESSION["pw"], $_SESSION["db"]);` with `$conn = new mysqli($ep, $un, $pw, $db);` in /var/www/html/lifeexpectancy.php.
2. THE fix SHALL be applied via sed or equivalent command in the User_Data script so that every new instance launched by the ASG includes the correction.
3. WHEN the fix is applied, THE Life Expectancy query (Query 3) SHALL return valid data from the Countrydata_Final_Table.
4. THE fix SHALL NOT alter any other files or queries in the PHP application.

### Requirement 15: Project Deliverables and Documentation

**User Story:** As a student team, I want to produce all required deliverables including architecture diagram, functional application, and design documentation, so that the project meets the course evaluation criteria.

#### Acceptance Criteria

1. THE project SHALL include an architecture diagram in Mermaid format showing all AWS components and their relationships.
2. THE project SHALL provide a functional PHP application accessible via the ALB DNS endpoint.
3. THE project SHALL include a document summarizing design decisions and architectural choices.
4. THE project SHALL include a security evaluation describing how the architecture protects against unauthorized access.
5. THE project SHALL include a scalability evaluation describing how the architecture handles increased load.
6. THE project SHALL be demonstrable in a live presentation showing the application responding to all 5 queries.

### Requirement 16: Lab Environment Constraints Compliance

**User Story:** As a student working within AWS Academy Learner Lab, I want the infrastructure to comply with all lab constraints, so that the project operates within budget and service limitations.

#### Acceptance Criteria

1. THE Terraform SHALL deploy all resources in the us-east-1 region exclusively.
2. THE Terraform SHALL use t2.micro instance type for all EC2 instances to minimize costs.
3. THE Terraform SHALL NOT configure HTTPS or custom domain names.
4. THE Terraform SHALL NOT configure user authentication for the web application.
5. THE Terraform SHALL provision only one RDS instance in the account.
6. THE Terraform SHALL use Amazon Linux 2023 as the AMI for all EC2 instances.
7. THE infrastructure SHALL operate within the Learner Lab budget constraints by using appropriately sized resources.
